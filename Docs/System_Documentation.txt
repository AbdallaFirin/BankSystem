1. System Overview 
 
The Bank Management System (BMS) is a full-stack web application designed to manage the complete 
operations of a multi-branch bank. It provides secure, role-based access to three categories of users: 
System Administrators, Bank Staff, and Customers. 
 
1.1 Core Objectives 
• Provide a secure, role-based platform for all bank staff operations 
• Implement a double-entry General Ledger ensuring financial integrity 
• Support multiple branches with centralized data and isolated operations 
• Enforce an atomic transaction model preventing money loss or duplication 
• Maintain a complete, immutable audit trail of all system activities 
• Provide customers with a self-service portal for account management

5.4 RBAC Enforcement in Laravel 
Every protected API route is wrapped with the CheckPermission middleware. The middleware queries 
the role_permissions table using the authenticated staff member's role_id and the required permission 
key. If no matching row exists, the request is blocked with HTTP 403 and the attempt is recorded in the 
staff_audit_log. 
 
How Permission Check Works (Laravel Middleware) 
1. Request arrives with Bearer token in Authorization header 
2. Sanctum validates token → loads authenticated Staff model 
3. CheckPermission middleware receives required permission key from route definition 
4. Query: SELECT 1 FROM role_permissions JOIN permissions WHERE staff.role_id AND 
permission_key = ? 
5. Row found → ALLOW, continue to Controller 
6. No row found → INSERT into staff_audit_log (result: denied) → return HTTP 403

6. Multi-Branch Architecture 
 
The system supports an unlimited number of branches. All branches share a single central MySQL 
database — there is no per-branch database or replication. Branch isolation is enforced at the 
application layer through the BranchScope middleware and the branch_id column present on every 
relevant table. 
 
6.1 Core Design Principles 
• Single central database — all branches read and write to the same MySQL instance 
• Every record carries branch_id — accounts, transactions, ledger entries, staff are all tagged 
• BranchScope middleware auto-appends WHERE branch_id = ? to all queries for branch-
restricted staff 
• Super Admin and Internal Auditor have no branch_id restriction — they see all data 
• Adding a new branch requires only inserting one row into the branches table — no code change 
 
6.2 Customer Visiting Any Branch 
A customer whose home branch is Branch A (Mogadishu) can walk into Branch B (Garoowe) and be 
served. Because all branches share one database, the Garoowe cashier's query returns the customer's 
account instantly. The resulting transaction is recorded with branch_id = Garoowe, while the account's 
home_branch_id remains Mogadishu. 
 
6.3 Inter-Branch Transfer — 4 Ledger Entries 
When a customer in Branch A transfers money to a customer in Branch B, the system uses a central 
inter-branch clearing account to ensure each branch's books balance independently.

7. General Ledger (GL) System 
 
The General Ledger is the financial backbone of the entire banking system. It is built on the principle of 
double-entry bookkeeping, a method used in every bank worldwide since the 15th century. Every single 
movement of money is recorded as two equal and opposite entries — a debit and a credit — ensuring 
perfect mathematical balance at all times. 
 
7.1 The Three Laws of the Ledger 
 
Law 1 — Every Transaction Creates Exactly Two Entries 
A DEBIT entry (money leaves one account) and a CREDIT entry (money arrives in another). 
Both entries carry the same transaction_id, linking them permanently. 
If a DEBIT exists without a matching CREDIT in the database, money has disappeared — the system 
can detect this automatically. 
 
Law 2 — Ledger Entries Are Append-Only (Never Updated or Deleted) 
Once written, a ledger_entry row is permanent. No UPDATE or DELETE is ever executed on this 
table. 
If a mistake is made, a reversal entry is written — a new pair of entries that mathematically cancels 
the original. 
This preserves complete financial history and satisfies regulatory compliance requirements. 
 
Law 3 — Balance Is Always Calculated, Never Stored 
The accounts table does NOT have a balance column that gets updated on every transaction. 
Balance is always computed on demand: SUM(credits) - SUM(debits) for a given account_id. 
This means the balance is always 100% accurate regardless of crashes, failures, or partial writes. 
Formula: current_balance = SUM(amount WHERE entry_type=credit) - SUM(amount WHERE 
entry_type=debit)

7.3 Atomic Transaction Implementation in Laravel 
Every multi-entry ledger operation is wrapped inside Laravel's DB::transaction() closure. MySQL 
automatically rolls back all statements if any exception is thrown before the closure completes. 
 
// LedgerService.php — Transfer between two accounts 
public function transfer(Account $from, Account $to, float $amount, Staff $staff): 
Transaction 
{ 
    return DB::transaction(function () use ($from, $to, $amount, $staff) { 
  
        // Step 1: Create parent transaction record 
        $txn = Transaction::create([ 
            'reference'      => 'TXN-' . strtoupper(uniqid()), 
            'type'           => 'transfer', 
            'status'         => 'pending', 
            'amount'         => $amount, 
            'initiated_by'   => $staff->id, 
            'branch_id'      => $staff->branch_id, 
        ]); 
  
        // Step 2: Check sufficient balance 
        if ($from->balance < $amount) { 
            throw new InsufficientFundsException('Balance too low'); 
        } 
  
        // Step 3: Write DEBIT entry (money leaves source) 
        LedgerEntry::create([ 
            'transaction_id' => $txn->id, 
            'account_id'     => $from->id, 
            'branch_id'      => $from->home_branch_id, 
            'entry_type'     => 'debit', 
            'amount'         => $amount, 
            'balance_after'  => $from->balance - $amount, 
        ]); 
  
        // Step 4: Write CREDIT entry (money arrives at destination) 
        LedgerEntry::create([ 
            'transaction_id' => $txn->id, 
            'account_id'     => $to->id, 
            'branch_id'      => $to->home_branch_id, 
            'entry_type'     => 'credit', 
            'amount'         => $amount, 
            'balance_after'  => $to->balance + $amount, 
        ]);

7.4 Balance Calculation in Laravel (Eloquent Accessor) 
 
// Account.php Model — Balance is never stored, always calculated 
public function getBalanceAttribute(): float 
{ 
    $credits = $this->ledgerEntries() 
                    ->where('entry_type', 'credit') 
                    ->sum('amount'); 
  
    $debits  = $this->ledgerEntries() 
                    ->where('entry_type', 'debit') 
                    ->sum('amount'); 
  
    return (float) ($credits - $debits); 
}

8. Transaction & Approval Workflow 
 
8.1 Transaction Status Lifecycle 
 
Status Description 
PENDING Transaction created but not yet processed. Starting state for all transactions. 
AWAITING_APPROVAL Amount exceeds staff limit. Moved to pending_approvals table for 
supervisor/manager action. 
SUCCESS All ledger entries committed. Money successfully moved. Final state. 
FAILED An error occurred during processing. DB::transaction() rolled back. No ledger 
entries saved. 
REVERSED A previously successful transaction was cancelled. Reversal ledger entries 
written. 
 
8.2 Approval Escalation Flow 
• Teller initiates transaction → system checks amount against role txn_limit 
• Amount within limit → process immediately, write ledger entries, status = SUCCESS 
• Amount exceeds Teller limit → insert into pending_approvals (approver_role = Teller Supervisor) 
• Teller Supervisor reviews queue → approves or rejects 
• Amount exceeds Supervisor limit → escalate again (approver_role = Branch Manager) 
• Branch Manager approves → LedgerService processes the transaction 
• Any rejection at any level → transaction status = FAILED, customer notified 
 
8.3 Failed Transaction Detection 
Staff can detect any stuck or failed transactions using the following query. Any transaction in PENDING 
status for more than 60 seconds is flagged for investigation: 
 
Monitoring Query for Stuck Transactions 
SELECT * FROM transactions 
WHERE status = 'pending' 
AND created_at < NOW() - INTERVAL 60 SECOND 
ORDER BY created_at ASC; 
 
The Accounting Officer runs this daily as part of ledger reconciliation. 
Any result here means a transaction is stuck and requires manual investigation.

10. Security Design 
 
 
Security Layer Implementation 
Password Hashing All passwords hashed with bcrypt (cost factor 12) before storage. Plain-text 
passwords are never stored or logged. 
API Authentication Laravel Sanctum issues per-session bearer tokens. Tokens are stored 
hashed in personal_access_tokens. Logout revokes the token immediately. 
Role-Based Access CheckPermission middleware on every protected route. Permission check is a 
database query — not a code condition. Roles can be changed without 
redeploying. 
Branch Isolation BranchScope middleware auto-injects WHERE branch_id = ? into all Eloquent 
queries for branch-restricted staff. Cannot be bypassed by the frontend. 
Input Validation All request inputs validated using Laravel Form Request classes before 
reaching controllers. SQL injection is prevented by Eloquent parameterized 
queries. 
Audit Logging Every API call by a staff member — including 403 blocks — is recorded in 
staff_audit_log with IP address, timestamp, and result. Table is append-only. 
HTTPS Only All communication between Vue.js frontend and Laravel API must use HTTPS 
in production. HTTP requests are redirected automatically. 
Token Expiry Sanctum tokens expire after configurable time (recommended: 8 hours for 
staff sessions). Expired tokens are rejected and the user must re-
authenticate. 
Immutable Ledger No UPDATE or DELETE is permitted on ledger_entries table. MySQL user for 
the application has INSERT and SELECT privileges only on this table.
